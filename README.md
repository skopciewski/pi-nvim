# pi-nvim

forked from [carderne/pi-nvim](https://github.com/carderne/pi-nvim)

## How it works

The pi side is the vendored pi-nvim extension, which opens a Unix socket for each pi session. The **Neovim plugin** (`lua/pi-nvim/`) finds the socket of the current project, connects to it via libuv, and sends context from the editor to pi. Every context command opens the same floating dialog: Enter with an empty prompt inserts context into pi's editor; Enter with a typed prompt submits it to the model. Windows is not supported.

### Session discovery

Each pi session listens on `<dir>/<hash>-<pid>-<random>.sock` and writes a manifest `<socket>.info` (`socket`, `cwd`, `projectRoot`, `pid`, `startedAt`) next to it. The project root is the nearest ancestor of the cwd that contains `.git` (a directory or a worktree/submodule file), or the cwd itself. `cwd` remains the actual session starting directory; `projectRoot` is the checkout root as seen by pi. `<dir>` is `<project root>/tmp` when that directory exists, otherwise `/tmp/pi-nvim-sockets`.

Keeping the socket in the project directory lets Neovim on the host reach pi running in a container that has the project volume-mounted, because the container's `/tmp` is not visible from the host. Create `tmp/` in the project (and ignore it in git) before starting pi.

The plugin picks the socket in this order:

1. `socket_path` from `setup()`, if configured. A missing path means no session; it does not fall back to a pin or discovery. Only existence is checked, not the file type.
2. The session chosen in `:PiSessions`, until it stops accepting connections.
3. The newest session in `<project root>/tmp`.
4. The newest session in `/tmp/pi-nvim-sockets` whose `projectRoot` matches the local project root. Older manifests without `projectRoot` fall back to matching `cwd` inside the project.

Sessions of other projects are never chosen automatically. `:PiSessions` lists the sessions in this project's `tmp/` and all sessions in `/tmp/pi-nvim-sockets` (any project), so you can pin one explicitly; sessions living in another project's `tmp/` are not visible from here. Discovery uses Neovim's effective cwd, including `:lcd` and `:tcd`. The result is cached and rescanned only when the cwd or one of the two directories changes.

If a discovered or pinned session refuses a connection, the plugin clears its pin and discovery cache, and deletes the leftover socket and its manifest (pi exited without cleanup). It deletes only names written by the extension, and only if the path still holds the socket that refused. Unbound delivery then retries once with a fresh lookup and rebuilds any file references for the replacement session. Unified dialogs bind delivery to the displayed session. Bound delivery, also available via the public Lua API, runs the same cleanup, but never retries or switches targets. An explicitly configured `socket_path` is neither cleaned up nor retried.

### File paths across host and container

File references generated by `:PiFile`, `:PiSelection`, `:PiBuffer`,
and `:PiDiagnostics` are **absolute paths in the displayed target session's filesystem**,
not host paths or paths relative to cwd. Virtual and unnamed buffers use labels
instead of paths. The dialog displays the local file name, context kind, and
target session above a multiline prompt.

The manifest in the shared `<checkout>/tmp` directory pairs the local checkout
root with pi's `projectRoot`. For example:

```text
Neovim root: /home/user/worktrees/project/feature-a
pi root:     /mnt/agent-share/project/worktrees/feature-a
Local file:  /home/user/worktrees/project/feature-a/src/example.lua
Sent path:   /mnt/agent-share/project/worktrees/feature-a/src/example.lua
```

The same mechanism works when both roots are identical. Neither process needs
to start at the root; cwd subdirectories do not affect the resulting reference.
Each worktree must share its own `tmp/` directory and socket with the host;
different checkouts must not point their `tmp/` directories at one common socket
store. Create that directory **before starting pi**, including in a fresh worktree;
the container's global socket directory is not visible on the host.

The local socket address comes from where the manifest was found, never from
the container's `socket` field. Older manifests without `projectRoot` can infer
the remote root from an advertised `<root>/tmp/<name>.sock` address. Global
sockets and custom socket locations without a shared-root pairing assume the
same filesystem path namespace, using the manifest's project root (or the
locally resolved cwd for older manifests).

Dialog file references use the displayed target session and its captured checkout
metadata. Unbound Lua API delivery rebuilds references if a connection retry
selects a different session. Files outside the selected session's checkout,
including symlinks leading outside it, are rejected with an error. Symlinked
checkout paths and new, unsaved files inside a checkout are supported. Unnamed
buffers are labeled `(unnamed buffer)` rather than assigned a file path.
Terminal, scratch, and other virtual buffers can send contents, selections, and
diagnostics with a `(buffer: ...)` label, never an invented checkout file path.
`:PiFile` requires a real file buffer; `:PiPrompt` sends only the entered prompt,
regardless of the current buffer.
A fixed socket without usable manifest metadata still accepts plain prompts and
pings, but cannot accept automatically generated file references.

All sends use the selected socket, even if a pi terminal buffer is open in
Neovim. The plugin no longer sends bracketed-paste input to the first terminal
named pi, so that terminal cannot override `:PiSessions` or the path mapping.
Paths typed manually in a prompt are not rewritten.

## Install

### Neovim side

With [lazy.nvim](https://github.com/folke/lazy.nvim):

```lua
{ "carderne/pi-nvim" }
```

Then in your config:

```lua
require("pi-nvim").setup()
```

The only supported option is `socket_path`; unknown option names raise an error.
Defaults:

```lua
require("pi-nvim").setup({
  socket_path = nil, -- nil = discover; a fixed path must exist, with no fallback (see above)
})
```

## Usage

Start pi in one terminal (or container) and Neovim in another, both in the same project. The pi extension opens a socket on session start.

### Commands

| Command              | Description                                                  |
| -------------------- | ------------------------------------------------------------ |
| `:PiPrompt`          | Open the unified dialog with no file attached                 |
| `:PiFile`            | Open the unified dialog with a reference to the current file  |
| `:PiSelection`       | Open the unified dialog for a selection, range, or current line |
| `:PiBuffer`          | Open the unified dialog with the whole buffer                 |
| `:PiDiagnostics`     | Open the unified dialog with the current buffer's diagnostics |
| `:PiPing`            | Check if pi is reachable                                      |
| `:PiSessions`        | List running pi sessions (see Session discovery) and pin one  |

`:PiDiagnostics` captures all diagnostic severities and sources known to Neovim
for the current buffer only, when the dialog opens. The text starts with
`Diagnostics for <ref>:`, followed by a note if the buffer has unsaved changes,
then one line per diagnostic: one-based line and byte column, severity, source
and diagnostic code (when available), and diagnostic text, sorted by position.
Continuation lines of multiline messages are indented by two spaces. It does not
send buffer contents or run a new analysis. If the buffer has no diagnostics, the
command notifies `No diagnostics in current buffer` and does not open the dialog.
Diagnostic positions come from Neovim's most recent diagnostic results, which can
lag behind edits. An empty prompt inserts the diagnostic text into pi's editor;
a typed prompt submits it with your question.

### The unified dialog

`:PiPrompt`, `:PiFile`, `:PiSelection`, `:PiBuffer`, and `:PiDiagnostics` open
the same info bubble above a multiline prompt bubble. It shows the file, the
context kind, and the target session:

```text
 File: src/example.lua
 Context: selection, 3 lines (10-12)
 Session: /workspace/project [pid 42, 07:23] auto
```

The context line is one of `Context: prompt only` (with `File: not attached`),
`Context: file reference`, `Context: selection, <N> lines (<a>-<b>)`,
`Context: buffer, <N> lines`, or `Context: diagnostics, <N> items`. Unnamed
buffers show `File: (no file)`; virtual buffers show their buffer name.

The session origin is `config`, `pinned`, or `auto`, following the discovery
priority above. Missing metadata is shown as `?`; the start time is displayed
without timezone conversion. Long session cwd paths are shortened from the left
by display cells, preserving the most specific tail. No reachable target shows
`Session: none`, but the dialog still opens. With `:PiSelection`, the selected
source lines stay highlighted until the dialog closes.

One rule applies to every context kind:

- **Enter with an empty or whitespace-only prompt** inserts the context into
  pi's interactive editor without starting a model turn. Neovim keeps focus and
  reports `Inserted into pi editor`.
- **Enter with a typed prompt** submits the trimmed prompt with the context.
  Neovim reports `Sent to pi`.

| Command        | Insert (empty prompt)                               | Submit (typed prompt)                                         |
| -------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| `:PiPrompt`    | nothing; warns `Nothing to send`, dialog stays open | the prompt text only                                          |
| `:PiFile`      | the file reference                                  | `File: <ref>`, a blank line, the prompt                       |
| `:PiSelection` | `<ref> lines <a>-<b>:` and a fenced block           | the prompt, a blank line, `From <ref> lines <a>-<b>:` and the block |
| `:PiBuffer`    | `<ref>:` and a fenced block of the whole buffer     | the prompt, a blank line, `File: <ref>` and the block         |
| `:PiDiagnostics` | `Diagnostics for <ref>:`, the optional unsaved-changes note, and the diagnostic lines | the prompt, a blank line, then the insert text |

Fenced blocks carry the filetype captured at open.

- `:PiPrompt` always opens. It sends no file reference, so it also works with a
  configured socket whose manifest lacks checkout metadata. Commands that need a
  generated file reference reject such a socket with an error and keep the dialog
  open; virtual and unnamed buffers send their labels and are accepted.
- `:PiFile` warns `No file open` and does not open in an unnamed, virtual, or
  terminal buffer, so pi never receives an invented path.
- `:PiBuffer` always opens and captures the buffer contents when it opens.
- `:PiDiagnostics` notifies `No diagnostics in current buffer` and does not open
  when the current buffer has none. Diagnostics are captured when it opens.

For every context kind:

- Delivery is bound to the displayed session's socket and checkout, with no
  fallback to another session. Enter resolves the target again; if it changed,
  it only refreshes the preview. Another Enter is required to deliver.
- A missing session or failed delivery keeps the dialog and prompt open. A
  failure refreshes the preview; retrying never silently switches targets.
  Delivery outcomes are reported once by the transport, not again by the dialog.
- Enter is ignored while delivery is in flight. Closing the dialog does not
  cancel an already-written request. A late response never touches the closed
  dialog's windows or buffers.
- Only one unified dialog can be open. Opening another closes the previous one
  first, saves its prompt, and restores that draft in the replacement dialog.
  This also applies when the previous dialog has a delivery in flight.
- **Esc**, **Ctrl-C**, or leaving the prompt window closes the dialog. The trimmed
  prompt becomes an in-memory draft, restored when the next unified dialog opens.
  Closing with an empty prompt or successfully delivering clears the draft. A
  failure after closing retains the prompt captured at close. To insert after
  restoring a draft, clear the prompt first.
- Tab has no dialog-specific binding. The prompt grows with its contents, up to
  six rows, including when a multiline draft is restored.

`:PiSelection`, `:PiBuffer`, and `:PiDiagnostics` capture their text and source
buffer label (selection and buffer also the filetype) when the command opens.
Virtual and terminal buffers keep their buffer labels, such as
`(buffer: term://…)`, rather than invented file references;
unnamed buffers use `(unnamed buffer)` in the message.

Without a range in normal mode, the command uses the current line. An explicit
range such as `:10,12PiSelection` uses whole lines, except when its two endpoints
match the last visual marks: that range uses the exact previous visual region.
Visual `:` mappings use those marks and their visual type; visual `<Cmd>` mappings
use the active region and leave visual mode before opening. Characterwise and
blockwise selections are exact. An empty region warns `Empty selection` and does
not open a dialog.

Newer draft decisions take precedence over older outstanding deliveries. If you
close another unified dialog before an older delivery completes, its late success
or failure cannot clear or replace the newer draft. This also protects a deliberate
empty close, an unchanged prompt saved again, or a newer successful delivery that
cleared the draft. An older delivery still reports its outcome once; it never
changes a newer open dialog's text.

### Additional keybindings

The plugin installs no default mappings. Add your own, for example:

```lua
vim.keymap.set("n", "<leader>cp", "<Cmd>PiPrompt<CR>")
vim.keymap.set("n", "<leader>cf", "<Cmd>PiFile<CR>")
vim.keymap.set("n", "<leader>cc", "<Cmd>PiSelection<CR>")
vim.keymap.set("x", "<leader>cc", "<Cmd>PiSelection<CR>")
-- Alternatively, a visual colon mapping:
-- vim.keymap.set("x", "<leader>cc", ":PiSelection<CR>")
vim.keymap.set("n", "<leader>cb", "<Cmd>PiBuffer<CR>")
vim.keymap.set("n", "<leader>cd", "<Cmd>PiDiagnostics<CR>")
vim.keymap.set("n", "<leader>cs", "<Cmd>PiSessions<CR>")
vim.keymap.set("n", "<leader>ci", "<Cmd>PiPing<CR>")
```

## Protocol

The socket accepts newline-delimited JSON:

```json
{"type": "prompt", "message": "your prompt here"}
{"type": "insert", "message": "context to append to the pi editor"}
{"type": "ping"}
```

Responses:

```json
{"ok": true}
{"ok": true, "type": "pong"}
{"ok": false, "error": "..."}
```

`prompt` submits to the model. `insert` appends to pi's interactive editor without
submitting and requires an extension with insert support; an older extension
rejects it rather than submitting it. A successful insert response means the
editor was updated, not that a model turn started.

This means you can also send prompts from any tool:

```bash
echo '{"type":"prompt","message":"hello"}' | socat - UNIX-CONNECT:tmp/<hash>-<pid>-<random>.sock
```

## Tests

Each suite runs headlessly without a test framework. Delivery and dialog tests
use real Unix sockets and temporary checkouts.

```sh
nvim --clean --headless -l tests/commands_spec.lua
nvim --clean --headless -l tests/discovery_spec.lua
nvim --clean --headless -l tests/diagnostics_spec.lua
nvim --clean --headless -l tests/context_spec.lua
nvim --clean --headless -l tests/delivery_spec.lua

```
